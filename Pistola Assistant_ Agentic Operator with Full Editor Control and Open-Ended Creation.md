# Pistola Assistant — Agentic Operator Plan
## Problem
The chat must be able to build or change *anything* the editor can represent, and IDE agents must have the same power. Prior task files (`TASK-ai-full-control.md`, `TASK-ai-full-creation.md`, `TASK-ai-chat-smarter.md`, `TASK-ai-chat-command-vision.md`) are all checked complete, yet the architecture still caps what the assistant can do:
* Planning is **regex router → single-shot JSON plan (≤25 actions) → one repair retry** (`editor/apps/editor/lib/assistant-ai-provider.ts:5300`). The model cannot query the scene, measure, search the catalog, or observe execution results inside a turn. Every new capability needs hand-written regex routes and prompt text in a ~5,600-line file.
* Creation building blocks are narrow: architectural nodes, a fixed `CATALOG_ITEMS` list, proxies limited to `asset.primitive: 'box'` (`editor/packages/core/src/schema/nodes/item.ts:83`), CAD previews limited to box/cylinder (`editor/packages/core/src/schema/nodes/cad-body.ts:5`), "ears/shell/face-extrude" implemented as attached boxes, MAC parts imported with a placeholder box preview. No general primitives, no materials/colors on existing nodes (except zone color), no asset import by URL, no sketch-entity authoring action, no `create_site`/`create_building`, no camera focus-on-node.
* IDE agents (`editor/tooling/pistola-mcp/src/index.ts`) can plan/execute/chat but only read a shallow workspace snapshot (phase, selection, node count).
* Coverage is asserted by checklists, not enforced: nothing fails when a new command-palette entry, tool, or panel mutation ships without an assistant action.
## Current State (verified)
* Contract and executor live in `editor/packages/editor/src/lib/assistant/` (`types.ts` = 82 action types, `execute.ts` = validation + rollback + `$ref_N` forward refs, `builders.ts`, `context.ts`, `sequence-validation.ts`).
* Planner, providers (Codex SDK / OpenAI Responses / OpenRouter / Gemini fallback), deterministic router, continuation, task-plan and image grounding live in `editor/apps/editor/lib/` (`assistant-ai-provider.ts`, `assistant-agent-router.ts` is only keyword classification into structure/furnish/cad/layout labels, `assistant-task-plan.ts`, `assistant-turn-sequence.ts`, `assistant-target-resolution.ts`).
* Panel: `editor/apps/editor/components/editor/AiAssistantPanel.tsx` (`requestAssistantTurn` at line 1080, `executeTurnChunk`, `runAssistantTurnSequence`). MCP bridge: `editor/apps/editor/lib/workspace-bridge.ts` + `components/editor/WorkspaceBridge.tsx` (command queue executed in the live tab).
* Validation commands: `cd editor && bun run check-types`, `bun run lint`, `bun test <files>`, `bun run acceptance:assistant`.
* Working tree has ~30 uncommitted modified files across all packages (MAC integration, auth, helpers). Baseline must be established before any refactor.
## Design Decisions
* Keep the deterministic router as the fast, free path for simple commands; add an **agentic operator loop** behind it for everything else instead of adding more regex.
* The scene lives in the browser, so the loop is **client-driven**: the panel (or WorkspaceBridge for MCP) calls `POST /api/assistant/agent/step` with the transcript and prior tool results; the server makes one provider call with tools and returns either `tool_calls` (fulfilled locally in the tab) or a `final` turn. Stateless server, no new infra, package boundaries intact (`apps/editor` orchestrates, `packages/editor` validates/executes, `core`/`viewer` stay assistant-agnostic).
* Every capability is registered once in a **capability registry** (`packages/editor`) that drives: the Zod action union, validators/executors, planner tool descriptions, MCP tool descriptions, deterministic aliases (EN/ES), and a coverage test. Adding a capability = one module; forgetting one = failing test.
* Widen creation with **general primitives + compounds + appearance + asset import + parametric recipes**, so the agent has enough building blocks to compose arbitrary objects; keep MAC for engineered parts and `execute_cad_brief` for prismatic CAD. External text-to-3D generators stay optional and behind an interface (tradeoff surfaced in Phase 4).
* Safety stays as-is or stricter: 25 actions per execute call, per-turn caps on tool rounds/total actions/wall-clock, one rollback snapshot per turn ("undo last assistant turn"), destructive actions gated by the existing autopilot/review policy, `ask_user` ends the turn in clarify mode, no fake success.

## Phase 2 — Agentic Operator Loop
- [ ] New server module `editor/apps/editor/lib/assistant-agent/` : `tools.ts` (tool JSON schemas derived from the registry plus read tools), `step.ts` (one provider round: messages + tool results → provider call → normalized `tool_calls | final`), provider adapters using native tool calling for OpenAI Responses, OpenRouter (OpenAI-compatible), Gemini function calling; Codex initially falls back to the single-shot planner (note: later option is a Codex thread with `pistola-mcp` tools).
- [ ] Route `POST /api/assistant/agent/step` (auth via `requireRouteAuthSession`, same error classification as `app/api/assistant/plan/route.ts`). Request: prompt, chatMode, transcript, toolResults, budgets, shaped workspace context (`shapeAssistantPlanningContext`). Response: `{ kind: 'tool_calls', calls[] } | { kind: 'final', turn: AssistantTurnResult }`.
- [ ] Client tool fulfillment in `editor/packages/editor/src/lib/assistant/agent-tools.ts` (pure functions over `useScene`/`useViewer`/`useEditor`, no UI): read tools `inspect_scene` (filter by level/type/name/bbox, paginated summaries via `summarizeAssistantNode`), `get_nodes`, `measure` (bounds, distance, wall length, zone area via `lib/space-detection.ts`, free floor space), `search_catalog`, `list_capabilities`, `get_workspace_state`; write tools `validate_actions` (dry-run through `validateAssistantPlan`), `execute_actions` (through `executeAssistantPlan` with `reviewConfirmed` per policy, returns created ids, warnings, errors), control tools `ask_user`, `finish`.
- [ ] Loop driver `apps/editor/lib/assistant-agent/run-agent-turn.ts` used by both the panel and `WorkspaceBridge.tsx`: captures one undo snapshot at turn start, enforces budgets (default 12 tool rounds, 25 actions per execute, 150 actions per turn, 5 min wall-clock, stop button), applies destructive-review policy (pause loop and show review card; resume on confirm), converts `finish`/`ask_user` into the existing `AssistantTurnResult` shape so review cards, undo, session memory and messages keep working.
- [ ] Routing rule in `createAssistantTurnResult`: deterministic router first; if it yields nothing (or the request is classified moderate/complex, or `chatMode` is create/refine with an image), use the agent loop when the provider supports tools; otherwise legacy single-shot. Timeout fallbacks unchanged.
- [ ] Panel UX: streaming step timeline (tool name, short observation, executed actions), Stop, and the existing "undo last assistant turn". No new chat modes.
- [ ] Tests: unit tests for tool fulfillment (fixtures scenes), step normalization per provider (mocked responses), budget enforcement, review pause/resume, rollback on failure, and replay tests where a recorded tool-call transcript must reproduce the same scene.

## Phase 4 — Compositions, Recipes, and Generator Adapters
- [ ] Recipe library `packages/editor/src/lib/assistant/recipes/` : parametric builders returning validated actions (table, chair, desk, bed, shelf, cabinet, stairs, railing, fence, column/beam, pergola, tree, lamp post, sign, car proxy). Action `create_from_recipe({ recipe, params, placement })` plus `list_recipes` read tool so the agent discovers them; recipes are also usable by the deterministic router.
- [ ] Approximation policy in the system prompt: prefer catalog match → recipe → compound of primitives → CAD brief (prismatic) → MAC (engineered part) → explicit limitation. Every approximation states assumptions.
- [ ] Optional generator adapter interface `apps/editor/lib/assistant-agent/generators/` (`generateMesh(prompt) → GLB url`) with MAC as the first implementation; an external text-to-3D provider (for example a Mint MCP or hosted API) can be added later behind the same interface. Tradeoff to surface before adopting: network dependency, cost, licensing, non-editable meshes. Not required for this plan's acceptance.
- [ ] MAC import improvement: derive preview dimensions from the returned GLB bounds instead of the fixed placeholder box.

## Acceptance Gate
- [ ] "Create a red sphere 0.5 m on the table" builds a primitive parented/placed correctly without remote planning.
- [ ] "Build a small bookshelf with 4 shelves" produces an editable compound (recipe or primitives) with stated assumptions.
- [ ] "Make the sofa blue" and "hide all windows on level 2" execute via registry capabilities against resolved targets.
- [ ] "Put a window on the longest wall of the living room" requires observation: the agent inspects/measures, then places the window; the step timeline shows the inspection.
- [ ] "Import <glb url> as a lamp" creates an item with measured dimensions and it is reusable by name in the next prompt.
- [ ] "Build a small car" yields a proxy compound or MAC part with explicit approximation notes; never a fake success.
- [ ] The same six requests succeed through `pistola_agent` from an IDE agent with the editor tab open.
- [ ] Coverage test blocks merging any new palette command/tool/panel mutation without a registered capability.
- [ ] Every mutating turn is undoable with one action; destructive steps still honor the review policy; budgets stop runaway loops.
- [ ] `check-types`, `lint`, targeted tests, and `acceptance:assistant` (offline replay) pass.
## Risks and Notes
* Dirty working tree: refactors in Phase 1 touch the same files as the uncommitted MAC/auth work; establish a commit boundary first (user decision).
* Provider variance: tool-calling formats differ; normalize in adapters and cover with recorded fixtures. Codex SDK path stays on the single-shot planner until an MCP-backed thread is validated.
* Schema growth: new primitives/materials must default safely for persisted scenes (IndexedDB/Supabase); add a migration-style test loading old fixtures.
* Latency/cost: the loop adds rounds; keep the deterministic router first and cap rounds; show progress so the user is never waiting blind.
* Child agents are not proposed now because the tree is dirty (worktrees would miss uncommitted changes) and Phases 1→2→3 are sequentially dependent; after Phase 1 lands on a clean tree, Phase 3 (core/viewer primitives) and Phase 5 (MCP) are good candidates to delegate in parallel worktrees.
